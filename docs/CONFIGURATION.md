# Configuration and credentials

GitHub Actions deploys the single `ilien` target through AWS OIDC. This reference defines the runtime and deployment configuration boundary.

## GitHub Actions

Use environment-scoped Variables for non-secret values: `AWS_REGION`, `AWS_ROLE_ARN`, Terraform backend bucket/key, public domain, model identifiers and resource identifiers. Restrict the deployment environment to approved branches.

Use GitHub Secrets for externally supplied credentials needed during deployment. Never put these values in repository files, command-line arguments that are logged, public artifacts or Terraform variable/state values. Workflows must explicitly control masking, shell tracing and artifact inclusion.

AWS access uses GitHub OIDC and short-lived role sessions. Do not create `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` repository secrets for this deployment. Inspect the repository's actual OIDC subject configuration: newer repositories may use immutable owner/repository IDs. Trust must match the exact subject and `sts.amazonaws.com` audience, not a wildcard organization.

Non-secret channel Variables are `APP_DOMAIN`, `WHATSAPP_WABA_ID`, and `WHATSAPP_PHONE_NUMBER_ID`. The email domain is `mail.${APP_DOMAIN}`; DNS records are generated by Terraform. Existing Meta business identity is independent of the application name. No Meta access token is required by these AWS SDK adapters.

## Application runtime

AWS-native calls use workload IAM roles. GitHub Secrets are not a runtime secret store: the deployed application cannot fetch them on demand. Where an external runtime secret is necessary, deployment can securely provision its value into AWS Secrets Manager in a separate redacted step, outside Terraform state. Terraform manages the secret container and access policy; runtime reads the secret through its role. Provider-generated secrets should remain in AWS where possible, with only the secret ARN stored in GitHub Variables.

Do not duplicate or rotate a secret in competing systems without a defined owner. Avoid creating application secrets until the implementing component actually needs them.

## Communication identities

A recipient's Gmail address or personal WhatsApp number is not a business sending identity. SES sandbox recipients/senders require appropriate verification; email replies require a controlled receiving domain and receipt routing. WhatsApp requires a linked business account and registered sending number. Prefer a separate business sender rather than migrating a personal number. Never commit participant contact details into fixtures or examples.

References: [GitHub AWS OIDC](https://docs.github.com/en/actions/how-tos/secure-your-work/security-harden-deployments/oidc-in-aws), [AWS WhatsApp onboarding](https://docs.aws.amazon.com/social-messaging/latest/userguide/getting-started-whatsapp.html), [SES receiving](https://docs.aws.amazon.com/ses/latest/dg/receiving-email-concepts.html).


## AI configuration

The pinned regional model is `amazon.nova-lite-v1:0`, using the agent worker IAM role; no model API key or new GitHub secret is needed. Its exact model ARN is permitted in both the runtime boundary and worker policy. AI settings and approved knowledge are source-scoped operator API configuration with revision/audit history; see [AI](AI.md). The model does not receive contact credentials or choose the deployment model. Initial mode requires operator review of every effect. No customer knowledge is preloaded.

## Web hostname and TLS

`APP_DOMAIN` also selects the optional console hostname. Terraform requests an ACM DNS-validated certificate in us-east-1 and outputs `web_dns_records`. The deployment initially keeps `CUSTOM_DOMAIN_READY=false` (default), so certificate issuance does not block the working CloudFront URL. Add the generated validation CNAME and the application CNAME at the authoritative DNS provider, using the exact subdomain names and targets. Keep the validation CNAME for automatic certificate renewal; DNS-only records make validation/origin troubleshooting clearer.

After ACM reports ISSUED and the application DNS target is in place, set the GitHub environment variable `CUSTOM_DOMAIN_READY=true` and run the delivery workflow. Terraform then attaches the hostname/certificate to the existing CloudFront distribution, enforces TLS 1.2 or newer, allows the exact custom and CloudFront origins in API CORS, and registers both exact callback/logout URLs in Cognito. Activation fails its plan precondition if the certificate is not issued. No new database or second application is needed.

The browser selects its callback only from the server-configured exact allowlist, matching its current origin. This preserves PKCE session state on both the custom hostname and original CloudFront URL. It does not accept an arbitrary URL from a query parameter. Email identity/MX/DKIM records are separate from these web CNAMEs; retain them unchanged.
